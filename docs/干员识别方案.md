# 干员识别方案（含技能与模组）

> ## 实现状态（最终，2026-10-20）
>
> 本文是**设计稿**。实际落地时有两处改进，以实现为准：
>
> 1. **技能触发类型不用从视频读**：游戏数据 `skill_table.json` 里每个技能就有
>    `skillType`（`AUTO` / `MANUAL`）和 `spData.spType`（自动回复/攻击回复/受击回复）。
>    所以只要从面板认出**技能名**，触发类型直接查表 → 落到 `lib/skills.json` 的 `auto` 字段。
>    （原先设计的「比第一个字判手/自」已废弃，只在区域标定时留作参考。）
> 2. **名字识别实测可行**：把 433 个干员名用 `msyh.ttc` 渲染成 32×32 位图，和面板名字区
>    二值化字形做归一化互相关，**闭集匹配**。实测：
>    | 干员 | NCC | 第2名 | margin |
>    |---|---|---|---|
>    | 山 | 0.650 | 0.193 | **0.457** |
>    | 娜仁图亚 | 0.795 | 0.483 | **0.312** |
>
>    不需要 OCR 引擎。见 `lib/opername.cjs`。
>
> 3. **面板不一定出现**：实测 YW-1 只有 2 次部署时玩家打开了详情面板（4 次里认对 2 次）。
>    其余只能用占位名并在 `doc` 里标注。
>
> 4. **模组/技能等级/潜能仍然拿不到，且不写**（理由见第三节末）。

> 目标：从攻略视频还原出 copilot 作业里 `opers[]` 每一项的完整信息：
> 干员名、技能序号、技能用法、精英化、等级、技能等级、模组。
>
> 本文的字段定义全部来自 MAA 源码（不是猜），视频可见性来自实测帧。

## 一、MAA 认什么字段（源码确认）

### `opers[]` 每项的结构

| 字段 | 类型 | 取值 | 源码位置 |
|---|---|---|---|
| `name` | string | 中文名 | `CopilotConfig.cpp:63` |
| `skill` | int | **0~3**<br>0 = 默认技能 / 上次编队用的<br>1/2/3 = 第几个技能 | `AsstBattleDef.h:152` |
| `skill_usage` | int | 0 = 不自动用<br>1 = 有就用（Possibly）<br>2 = 用 X 次（配 `skill_times`）<br>3 = 自动判断时机（InTime） | `AsstBattleDef.h:117-124` |
| `skill_times` | int | 默认 1 | `AsstBattleDef.h:154` |
| `requirements.elite` | int | 0 / 1 / 2 | `AsstBattleDef.h:129` |
| `requirements.level` | int | 等级 | `:130` |
| `requirements.skill_level` | int | 1~7 普通；8/9/10 = 专一/专二/专三 | `:131` |
| `requirements.module` | int | **-1 = 不切换模组/无要求**<br>0 = 不使用模组<br>1 = 模组χ　2 = 模组γ　3 = 模组α<br>4 = 模组Δ　5 = 模组β | `:132` |
| `requirements.potentiality` | int | 潜能 |

### 两个必须知道的坑

**① `potentiality` 这个版本根本不读。**
`CopilotConfig.cpp:112` 是这么写的：

```cpp
// oper.requirements.potentiality = req_opt->get("potentiality", 0);
```

**整行被注释掉了。** 所以哪怕写进去也不生效，不用管。

**② `elite` 会被反推，写低了直接 LogError。**
`CopilotConfig.cpp:108-138`：

```cpp
int elite_require = oper.skill - 1;                       // skill 1→0, 2→1, 3→2
if (skill_level > 7) elite_require = max(2, ...);         // 专精 ⇒ 必须精二
else if (skill_level > 4) elite_require = max(1, ...);    // 7级技能 ⇒ 至少精一
if (module 存在) elite_require = max(2, ...);             // 有模组 ⇒ 必须精二
if (显式 elite < elite_require) LogError("...has higher elite requirement...")
```

也就是说：**写了 `module` 就必须 `elite >= 2`；写了 `skill_level >= 8` 也必须 `elite >= 2`。**

## 二、视频里能看到什么（实测分层）

### 层级 A — 作战详情面板（每个部署动作都会出现）

实测 YW-1 @16.9s，点开干员卡后左侧面板显示：

```
攻击范围图（黑底白格，形状唯一）
职业徽章（红底，先锋/近卫/…）
干员名：山              ← 白字，约 x 25..200, y 275..315（1920 空间）
LV 60
攻击 654 / 防御 442 / 法抗 0 / 阻挡 1
技能「横扫架势」
  自动回复 · 手动触发
技能描述文字（多行）
底部 tab：技能 / 特性 / 天赋
```

**可读**：名字、等级、技能名、技能回复类型（自动/手动）、攻击范围形状。
**不可读**：技能等级（专精几）、模组、潜能、精英化（只能间接推）。

### 层级 B — 编队界面（视频开头，不一定有）

显示每个干员的头像 + 名字 + **已选技能图标** + 精英化标记。

### 层级 C — 干员档案 / 养成页（攻略视频常见，但非必需）

**只有这一层**能看到：技能等级（专精）、模组（有无 + 哪个）、潜能。

## 三、逐字段映射方案

| copilot 字段 | 主要来源 | 备用来源 | 可靠性 |
|---|---|---|---|
| `name` | 详情面板名字 OCR | 编队界面 | **高**（已实测可见） |
| `level` | 详情面板 `LV N` | — | **高** |
| `skill`（1/2/3） | 详情面板**技能名** → 查「干员→技能名表」 | 技能图标匹配 | 中（依赖技能名表） |
| `skill_usage` | 详情面板「自动回复/手动触发」<br>+ 视频里是否手动点过 | 反推：不点 ⇒ 1（有就用） | 中高 |
| `skill_times` | 视频里该干员手动开技能的次数 | — | 中 |
| `requirements.elite` | 详情面板精英化标记 | 由 `level` + 技能等级反推 | 中 |
| `requirements.level` | 同 `level` | — | 高 |
| `requirements.skill_level` | ⚠ 作战面板**看不到** | 档案页 | 低 |
| `requirements.module` | ⚠ 作战面板**看不到** | 档案页 | 低 |
| `requirements.potentiality` | **MAA 不读，忽略** | — | — |

### 关于「看不到的字段」怎么处理 —— 重要

`requirements` 的语义是**"最低练度要求"**，不是"视频里用的是这个"。

```
不写 requirements  →  MAA 不检查，用玩家自己现有的练度
写了 module: 2     →  MAA 要求玩家有 γ 模组，否则报 Unavailable
```

所以对一份**给别人跑的攻略作业**：

- **模组、技能等级、潜能：建议省略**
  - 省略 = 不限制 = 谁都能跑
  - 写死 = 别人没这个模组/专精就跑不了
- **等级/精英化：可选**，想标注"至少这个练度"再写
- **技能序号 `skill`：必须写**
  - 这是**玩法相关**的，不同技能效果完全不同
  - 不写（=0）会沿用玩家上次编队的技能，可能完全跑错

**结论：模组和技能等级在作战面板拿不到，而且本来就不该写死。**
如果确实要还原（比如做"一模一样复刻"），必须视频里出现干员档案页。

## 四、识别流程

### 阶段 0：准备数据

| 数据 | 来源 | 状态 |
|---|---|---|
| 干员名 + 职业 + position + rangeId | `battle_data.json`（1384 人） | ✅ 已有 |
| 攻击范围形状 73 种 | `battle_data.json` 的 `ranges` | ✅ 已有 |
| 职业图标 9 个 | `template/Battle/OperRole/` | ✅ 已有 |
| **干员 → 3 个技能名** | **MAA 资源里没有** | ❌ **缺，需外部补** |
| 中文字体（渲染名字做模板） | Windows `msyh.ttc` / `simhei.ttf` | ✅ 有 |

**唯一的外部依赖：干员技能名表。** 用来把面板上的「横扫架势」映射成 `skill: 2`。
补法：从游戏 wiki / PRTS 抓一份 `{干员名: [技能1名, 技能2名, 技能3名]}` 的 JSON。

---

### 阶段 1：定位每个部署动作的「详情面板时刻」

复用已验证的链路：

```
① deploy.findBattleStart()          干员栏饱和度 + 连续 8 帧 → 战斗起点（实测 12s）
② deploy.scanBarChanges()           干员栏每 1.5 秒色块比对 → 部署窗口（实测 8 次）
③ posmask.findOrangeTile()          窗口内每 0.2s 找橙色斜纹格 → 放置格 + 时刻（实测 40.8%）
```

**详情面板持续时间**：从点开卡片到松手，约 0.5~1.5 秒。
在窗口内按 0.2s 步进取帧，取「面板可见」的那一帧。

**面板可见判据**：面板区域（`x 0..340, y 200..1000` @1920）整体亮度明显高于战场；
或用面板左上角的**攻击范围图**（黑底白格，高对比）做锚点。

---

### 阶段 2：读干员名

```
① 裁名字区：x 20..300, y 270..320 @1920（约 280×50）
② 二值化：白字黑底 → 取亮度 > 阈值的像素
③ 裁掉首尾空白列（MAA 的 OperNameAnalyzer 就是这么做的）
④ 与"渲染出来的 1384 个名字"逐个 NCC 比对
```

**为什么用渲染而不是 OCR**：
- 没有中文 OCR 引擎，也不想引依赖
- ffmpeg 能 `drawtext` + `msyh.ttc` 批量渲染，一次生成 1384 张模板
- 名字是固定集合（1384 个），闭集匹配比开放集 OCR 更可靠

**风险**：游戏字体与系统字体不同 → 提高分辨率、用 NCC、并做字形归一化（按包围盒缩放）。
**兜底**：同时用**攻击范围图**做交叉验证（范围形状只有 34 种合法值）。

---

### 阶段 3：读等级

```
裁 LV 数字区（名字下方，约 x 90..200, y 320..360 @1920）
数字模板匹配（0-9，10 个模板）→ 组装成整数
```
数字模板可从任意一帧的 `LV 60` 里抠出来，或用 drawtext 渲染。

---

### 阶段 4：读技能名 → 定 `skill` 序号

```
① 裁技能名区（面板中部，「自动回复/手动触发」上方一行）
② 二值化 + 裁空白列
③ 查「干员→技能名表」：把该干员的 3 个技能名各渲染成模板，NCC 取最高
④ 命中的 index = skill（1/2/3）
```

**这一步必须先有阶段 2 的名字**，因为候选技能只有该干员那 3 个 —— 候选集极小，非常可靠。

---

### 阶段 5：定 `skill_usage` 与 `skill_times`

判据来自两个信号：

| 信号 | 含义 |
|---|---|
| 面板上写「自动回复」+「手动触发」 | 该技能**需要手动点** |
| 面板上写「自动回复」+「自动触发」 | 技能自动放，`skill_usage = 0` 或不写 |
| 视频里该干员头像/头像旁出现技能释放特效 | 手动点过 |

```
自动触发                      → skill_usage = 0（不自动用，让游戏自己放）
手动触发 + 视频里没见手点      → skill_usage = 1（有就用）
手动触发 + 视频里点了 N 次     → skill_usage = 2, skill_times = N
摆完挂机（SkillDaemon）        → 整组用 SkillDaemon 动作兜底
```

---

### 阶段 6：定 `requirements`

```
elite:      面板有精英化徽章则读；否则由 level + skill_level 反推
level:      阶段 3 的结果
skill_level: 拿不到 → 省略（省略 = 无限制，更通用）
module:     拿不到 → 省略（写 -1 等价）
potentiality: 不写（MAA 不读）
```

**精英化反推表**（游戏规则：精0 上限 50，精1 上限 55~80，精2 上限 60~90）：

```
level ≤ 50                    → 可能是精0 或精1
level 51..70                  → 至少精1
level > 70                    → 精2
skill_level ≥ 8（专精）        → 必须精2（MAA 也会强制）
```

## 五、完整数据流

```
视频
 │
 ├─ ① 战斗起点（饱和度 + 8 帧持续）
 │
 ├─ ② 部署窗口（干员栏 1.5s 色块比对）
 │
 ├─ ③ 放置格 + 朝向 + 时刻（橙色斜纹格 + 邻格唯一非零 / 范围形状匹配）
 │
 ├─ ④ 详情面板帧（窗口内 0.2s 步进，取面板可见帧）
 │     │
 │     ├─ 名字     → NCC vs 渲染的 1384 个名字    → name
 │     ├─ LV N     → 数字模板匹配                 → level
 │     ├─ 技能名   → NCC vs 该干员的 3 个技能名     → skill
 │     ├─ 自动/手动 → 文字判据                     → skill_usage
 │     ├─ 攻击范围图 → 34 种形状 × 4 向匹配         → 交叉验证 name
 │     └─ 精英徽章  → 若有则读，否则由 level 反推   → elite
 │
 ├─ ⑤ 站位类型（放置格 buildableType：1→MELEE，2→RANGED）—— 校验用
 │
 ├─ ⑥ 技能就绪（干员上方亮黄菱形）→ SkillDaemon 兜底
 │
 ├─ ⑦ 倍速（开局一条 SpeedUp）
 │
 └─ ⑧ 时序（视频时间轴 + pre_delay）
        ↓
   copilot JSON → copilot.validate() 逐格校验
```

## 六、几个能立刻用的交叉验证

单靠 OCR 有错字风险，用下面几条当面校验：

| 校验 | 做法 | 能力 |
|---|---|---|
| **范围形状** | 面板的攻击范围图 vs 该干员 `rangeId` 的 4 向旋转 | 名字 + 朝向双重验证 |
| **职业图标** | 面板职业徽章 vs 该干员 `profession` | 名字验证 |
| **站位类型** | 放置格 `buildableType` vs 该干员 `position` | **能直接否掉错名字** |
| **阻挡数** | 面板「阻挡 N」 vs 该干员 subProfession | 辅助 |
| **攻击力** | 面板「攻击 654」 vs 该干员在 LV60/精2 的数值 | 强验证，但需要数值表 |

其中 **站位类型** 最省事：`buildableType=1` 的格子只能站 MELEE，如果我 OCR 出的名字是 RANGED，直接判定识别错误并要求重新识别。

## 七、缺口清单

| 缺口 | 影响 | 补法 |
|---|---|---|
| **干员 → 技能名表** | 无法定 `skill` 序号 | 从 PRTS/游戏 wiki 抓 `{干员: [技能1,2,3]}` |
| 中文字体渲染相似度 | 名字 NCC 可能不够 | 先渲染测试；不行就补「字形归一化」 |
| 精英徽章识别 | `elite` 只能反推 | 也可从攻击力数值反推（需数值表） |
| 干员数值表 | 无法用攻击力验证 | 同上，从 wiki 抓 |

**这四条的补法都是"抓一份 JSON"，不需要新算法。**

---

## 八、结论

**能做到**：`name`、`level`、`skill`、`skill_usage` —— 这四项覆盖了"给一份能跑的作业"所需的全部关键信息。

**做不到（且不应该做）**：`module`、`skill_level`、`potentiality` —— 作战面板不可见，且 `requirements` 是"最低要求"语义，写死反而降低通用性。

**唯一硬依赖**：干员技能名表。没有它就拿不到 `skill` 序号，作业里只能写 `skill: 0`（沿用玩家上次编队的技能，不可靠）。
